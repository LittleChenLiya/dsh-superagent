# dsh-superagent 与 TRAE宝 的定位对比

两者不是同一层产品：一个是以 run 为单位的批处理执行器，一个是以会话为工作单元、
带定时入口的持续型 agent。下面只写能落到证据上的差异，且只比四个可观察的维度——
调度粒度、断点续跑、成本可见性、界面形态。不比较模型效果、任务成功率或价格，
这几项没有同口径数据。

## 口径

| 对象 | 依据 | 可信度 |
| --- | --- | --- |
| dsh-superagent | 仓库 0.9.3 工作树：README、`docs/DONE.md`、`docs/e2e-2026-11-14.md` 及其 transcript、`lib/` 代码 | 可核验，本页每条都指向具体行为 |
| TRAE宝 | 团队内部的一份对照调研记录（非公开文档），其中列出该产品的 10 条机制 | 二手转述。本页引用时标"转述"；该产品没有在仓库内留下任何一手材料 |

因此本页对 TRAE宝 的每一句都加了限定。凡写成"未核实"的地方，是真的查不到，
不是暗示对方没有这个能力。

## 一句话

dsh-superagent 做的事是：拿一个目标，规划成互不依赖的子任务，并行跑完，合并成一份
报告，结束。TRAE宝 按转述是以会话为工作单元、覆盖任务分诊/记忆分层/定时触发的
持续型 agent。前者回答"这一份活怎么并行且不丢"，后者回答"一堆活怎么分诊、派发、
持续跟进"。问题不同，重叠在"派发"和"汇报"这两个环节。

## 1. 调度粒度

| | dsh-superagent | TRAE宝 |
| --- | --- | --- |
| 工作单元 | run：有 id、9 种状态、一条 run 一个落盘文件 | 会话：转述中写明"会话即工作单元"，带消息 id 追踪、可续聊 |
| 拆分依据 | 一次规划模型调用，产出互不依赖的叶子子任务 | 转述："最小必要派发 + 依赖排序"，有依赖的任务等输入 |
| 依赖图 | 没有。调度器没有拓扑波次，有先后关系的工作要自己串在一个子任务里 | 转述为有依赖排序；具体是 DAG 还是串行队列，未核实 |
| 并发 | 每个 run 默认 3 个子任务同时跑（硬上限 8）；同时活跃的 run 默认 2 条 | 未核实 |
| 触发方式 | 只有显式工具调用。一次 goal 一条 run | 转述：会话触发，另有定时任务入口；调度器细节未核实 |
| 重复派发 | 同一会话内同一目标（忽略大小写与空白）返回已有 run id，标 `deduped: true` | 转述为"不重复派发"，判定键未核实 |

这里最实质的差别是**工作单元的边界**。插件的恢复、预算、取消都绑在 run 上，
session 只是发起者；TRAE宝 按转述绑在会话上。绑 run 的代价是不能给一条 run
追加指令（只能新开一条或 resume），绑会话的代价是"哪些历史算这次工作的上下文"
需要另外定义。

## 2. 断点续跑

| | dsh-superagent | TRAE宝 |
| --- | --- | --- |
| 状态载体 | `<stateDir>/runs/<runId>.json`，临时文件加重命名；旁边有 `.lock`、`.cancel`、`.json.corrupt-<ts>` | 未核实 |
| 判定"还有没有人管这条 run" | 本地 pid 是否存活、心跳是否新鲜、有没有活进程持锁；共享状态目录只信心跳（超 90 秒回收） | 未核实 |
| 崩溃后的语义 | 重启时把无主 run 标为 `interrupted`，在跑的子任务回到 `pending`；`resume` 只跑没完成的，复用原规划，不重付规划费 | 转述为会话可续聊；宿主重启后是继续会话还是另起一个，未核实 |
| 实测记录 | 硬杀宿主 → `interrupted`（带 `reclaimed: …` 判定依据）→ `resume` → `completed`；已完成子任务保留原 child id，累计花销不丢 | 无 |

两种"续"不是一回事：插件验证的是**进程死掉之后**怎么办，会话型产品保证的是
**进程没死、对话继续**时怎么接着说。前者可以做到只重跑未完成的部分，后者在宿主
崩溃后的行为未核实。所以不存在"谁更可靠"，只有"你担心哪一种断"。

## 3. 成本可见性

| | dsh-superagent | TRAE宝 |
| --- | --- | --- |
| 单次运行记账 | 每条 run 打印实测的 input / output / 缓存命中 token / 调用次数；token 数由一个独立脚本对子会话日志逐条核对过 | 未核实 |
| 预算 | 两个硬上限（每次运行的调用数、token 数），在每次 spawn 之前检查并中断正在跑的子代理 | 未核实 |
| 价格 | 不自带任何模型价格；价格由运维在配置里填，未定价的模型打印 `unpriced`，总价按下界报 | 未核实 |
| 事后视图 | `watch` 面板显示"已用调用 / 上限"；HTML 报告含累计调用曲线与费用曲线（40 条真实 run） | 未核实 |

这一项上插件采取的是"账本放在工具返回值里"：不看任何界面，复制 run 块就能对账。
TRAE宝 是否提供等价数据，内部调研记录里没有涉及，未核实——**不做优劣判断**。

## 4. 界面形态

| | dsh-superagent | TRAE宝 |
| --- | --- | --- |
| 界面 | 没有界面。不加 UI、不改宿主代码，对外只有 6 个 `superagent_*` 工具，返回文本 | 转述：有卡片面板与健康状态聚合，结果回到 IM/PR 场景 |
| 运维旁路 | 两个只读工具，读同一批 run 文件：终端面板、自包含 HTML 报告 | — |
| 远程入口 | 可选 loopback HTTP，带进程级 bearer token，只在 `127.0.0.1`；没有 MCP server，没有远程模式 | 未核实 |
| 依赖 | 运行时依赖为空（`dependencies: {}`），只发 `lib/` 与 `bin/` 里的文件 | 未核实 |

形态差异直接决定适配场景：插件能塞进 headless、CI、脚本和别的 UI 里（用 HTTP 面），
代价是没有"人在界面里看进度"的体验；卡片面板那一类形态更适合人持续在场的协作，
代价是它需要一整套常驻服务与状态模型，不适合当成一次性的命令行依赖。

## 各自不适合的地方

**这个插件不适合**：一次模型调用能答的问题；必须在一个 turn 内结束的工作；中途需要
人工审批的步骤；需要多级委派（子代理深度固定为 1）；需要宿主内面板的人；把子代理
当成安全隔离边界的人。

**TRAE宝 不适合什么**：本页没有依据，不写。内部调研记录里也只有它能做什么，
没有它的限制清单。

## 怎么选

1. 目标是"跑完一次、交一份报告，进程挂了也不丢"——用这个插件。
2. 需要人一直在场、跨天跟进、按来源分诊和汇报——那是会话型产品的地盘，插件不提供。
3. 要把能力嵌进 CI、脚本或别的 UI，且不想引运行时依赖——插件（6 个工具 + 可选
   loopback HTTP）。
